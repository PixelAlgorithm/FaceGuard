# Fuse passive, light and identity signals in two seconds

The strongest entry for HID's "Can You Spot a Spoof?" challenge is a **passive-first, risk-adaptive kiosk**. The browser runs MediaPipe Face Landmarker for face lock, quality gating and a short random screen-colour "flash" during a roughly one-second capture. A CPU server in AWS ap-south-1 runs an ensemble of Apache-2.0 MiniFASNet anti-spoof models, a phone/screen object detector and an FFT moiré check. Identity is matched with Amazon Rekognition user vectors (`SearchUsersByImage` for 1:N, `CompareFaces` for 1:1), with InsightFace `buffalo_l` as the self-hosted fallback. A three-zone fusion rule returns ALLOW or DENY when the evidence is clear. Anything uncertain goes to REQUEST VERIFICATION. That path escalates in three steps: a recapture; then a randomized challenge, which always includes a mouth or cheek deformation because eye-cut paper masks let the attacker's real eyes blink through (Rekognition Face Liveness is an alternative here); then an email or on-screen OTP. Each attack type gets its own layered defense. Clear 2D-attack evidence returns DENY. A single mask cue, by contrast, only routes to REQUEST VERIFICATION, so that lighting artefacts do not reject legitimate employees. The design does two things at once. It keeps the common ALLOW path inside the 2-second budget (about 1.3–1.9 s by estimate), and it pushes the attacks a single RGB frame handles badly, namely high-resolution phone replays and masks, onto the light-reflection and challenge layers. Interactive AWS Face Liveness cannot sit on the critical path: AWS sizes sessions at roughly 10 seconds. The largest scoring opportunity is honesty. HID's slide quotes "99.4% accuracy" and "0.2% FAR", but a one-day test set cannot statistically support figures like these. Reporting per-attack APCER, BPCER and FMR/FNMR with rule-of-3 confidence bounds, in ISO/IEC 30107-3 vocabulary, will read as expertise to biometrics judges. Two licences are the main risks: InsightFace weights are non-commercial, and so is the CelebA-Spoof dataset. Kiosk lighting comes next, and Workshop-Studio-style sandbox restrictions after that. All of them need day-one fallbacks.

## A passive-first pipeline with a light-flash capture wins the two-second race

The prototype flow the organizers prescribe is Capture → Liveness → Face Authentication → Decision. The recommended architecture fills each stage with the cheapest signal that is strong against a specific attack. It also runs liveness and matching in parallel on the server rather than in sequence. A browser kiosk (React + Vite, fullscreen Chromium) does the work that needs 30 fps feedback. It sends a small evidence bundle to a single server endpoint, and that endpoint owns every security decision. AWS's own Amplify liveness component follows the same split: it runs on-device BlazeFace detection before streaming, and its documentation warns that authorization must be decided in the backend, never from a client-side `isLive` flag ([Amplify UI Liveness](https://ui.docs.amplify.aws/react/connected-components/liveness)).

```
Kiosk browser (React, fullscreen, ap-south-1 backend)
 ├─ getUserMedia + MediaPipe Face Landmarker (VIDEO mode, 478 landmarks, 52 blendshapes, pose matrix)
 ├─ Quality gate: 1 face, IOD ≥ 60–80 px, |yaw|,|pitch| ≤ 20°, blur, luma 60–200, eyes open
 ├─ Virtual-camera check on device labels (OBS, ManyCam, DroidCam…) → injection flag
 ├─ ~1 s capture: server-issued nonce + random 3–4 colour screen tint; per-frame skin chroma series
 └─ POST /authenticate {3–5 JPEG frames ~640 px, chroma series, landmarks, nonce, timestamps}
        ▼
 API Gateway HTTP API → FastAPI on EC2 c6i/c7i (CPU, warm)   [or Lambda container, provisioned concurrency]
   ├─ parallel A: SCRFD detect/align → MiniFASNetV2(2.7x) + MiniFASNetV1SE(4.0x) + facenox 128 INT8 (onnxruntime)
   │              + COCO detector (cell phone / laptop / tv box containing face) + FFT high-frequency ratio
   │              + flash-response correlation & 3D shading ratio (recomputed server-side)
   ├─ parallel B: Rekognition SearchUsersByImage (1:N) or CompareFaces (1:1 claimed ID)
   │              [fallback: InsightFace buffalo_l ArcFace cosine vs numpy template matrix]
   ├─ Fusion → ALLOW / REQUEST_VERIFICATION{recapture|challenge|otp} / DENY + reason codes
   ├─ DynamoDB (user, status, consent, TTL) · S3 SSE-KMS (audit frames, lifecycle 1–7 days)
   └─ CloudWatch EMF: decision latency p50/p95, score histograms, per-scenario counters
 Step-up: randomized 2-step active challenge (MediaPipe) · optional Rekognition Face Liveness · SES email OTP / on-screen TOTP
 Enrollment: liveness-checked capture ×3–5 → IndexFaces → CreateUser → AssociateFaces (+ local 512-d templates)
```

### Component choices and why each earns its place

The passive anti-spoof core is **minivision's MiniFASNet**. It is the only family that is drop-in, Apache-2.0, and fast on a CPU. MiniFASNetV1 and V2 run at **0.081 GFLOPs with about 0.4M parameters**, and the training adds a Fourier-spectrum auxiliary branch. The released detector fuses models trained at several crop scales and claims coverage of print, screen, silicone mask and 3D portrait attacks ([minivision](https://github.com/minivision-ai/Silent-Face-Anti-Spoofing)). Ready ONNX ports exist from yakhyo, which ships both V2 at 2.7x and V1SE at 4.0x ([yakhyo](https://github.com/yakhyo/face-anti-spoofing)), and from garciafido on Hugging Face ([garciafido](https://huggingface.co/garciafido/minifasnet-v2-anti-spoofing-onnx)). The TFLite version measured **2.13 ms p50 on a Raspberry Pi 5 CPU** ([LiteRT card](https://huggingface.co/litert-community/Silent-Face-Anti-Spoofing-LiteRT)), so PAD inference is a rounding error in the latency budget. A third vote comes from **facenox's retrained 128×128 MiniFASNetV2-SE**. It is Apache-2.0, about 600 KB in INT8, and reports **98.20% accuracy and 0.9984 ROC-AUC on CelebA-Spoof** ([facenox](https://github.com/facenox/face-antispoof-onnx)). One integration trap needs a test against a real image in hour one. Upstream `test.py` treats **class index 1 as "real"** and sums the softmaxes of both models ([test.py](https://raw.githubusercontent.com/minivision-ai/Silent-Face-Anti-Spoofing/master/test.py)), while the garciafido card claims a `[live, print, replay]` order.

RGB CNNs generalize poorly, so the CNNs need help. FLIP, a stronger CLIP-based research model, still averages **8.61% HTER zero-shot** on the WMCA/CeFA/SURF protocols, where masks appear, and its TPR at 1% FPR drops to 58–84% ([FLIP, arXiv](https://arxiv.org/html/2309.16649)). The cheapest complements are three. A COCO detector flags a "cell phone" (class 67), laptop or TV whose box contains the face ([Ultralytics coco.yaml](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/datasets/coco.yaml)). An FFT high-frequency energy check targets moiré, the same cue MiniFASNet's auxiliary branch learns. And the screen-flash response check comes from the Face Flashing protocol (NDSS 2018), which reached **98.8% liveness accuracy (97.3% worst case)**. It verifies response timing and checks that the reflection pattern comes from a 3D face rather than a flat or emissive surface ([Tang et al., NDSS 2018](https://www.ndss-symposium.org/wp-content/uploads/2018/02/ndss2018_03B-5_Tang_paper.pdf)). AWS's default `FaceMovementAndLightChallenge` uses the same idea, and AWS calls it "the best setting to maximize accuracy" ([AWS Face Liveness](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html)). rPPG is deliberately excluded. pyVHR is GPL-3.0 and its examples use 6-second windows ([pyVHR](https://github.com/phuselab/pyVHR)), which a 2-second budget cannot accommodate.

MediaPipe Face Landmarker covers active liveness and quality with a single model. It outputs **478 3D landmarks, 52 blendshapes (eyeBlink, jawOpen, mouthSmile…) and a 4×4 head-pose matrix**. It runs on the web only in IMAGE or VIDEO mode, and the blendshape and matrix outputs must be explicitly enabled ([MediaPipe guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)). The classic eye-aspect-ratio blink threshold is **t = 0.2** ([Soukupová & Čech, CVWW 2016](https://vision.fe.uni-lj.si/cvww2016/proceedings/papers/05.pdf)).

For identity, the recommendation is **Rekognition user vectors as the primary matcher**. Three reasons support it. It is commercially clean, it is the AWS-native showcase the sandbox requirement invites, and HID added Amazon Rekognition support to its own biometric camera in June 2024 ([Biometric Update](https://www.biometricupdate.com/?s=HID+Global+face+liveness)), which makes it a direct problem-solution-fit story. `SearchUsersByImage` returns a single similarity per enrolled UserId, with `UserMatchThreshold` defaulting to 80 and a `QualityFilter` option ([API reference](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_SearchUsersByImage.html)). It costs **$0.001 per image**, and the free tier includes 1,000 images per month ([pricing](https://aws.amazon.com/rekognition/pricing/)). The fallback, and the tool for controlled threshold calibration, is InsightFace `buffalo_l`: SCRFD-10GF plus ArcFace R50 trained on WebFace600K, scoring **LFW 99.83 and IJB-C TAR@FAR=1e-4 of 97.25**. Its 16 MB sibling `buffalo_sc` is roughly two IJB-C points weaker ([InsightFace model zoo](https://github.com/deepinsight/insightface/tree/master/model_zoo)). Running both matchers also gives the team a cross-check slide.

## Three-zone fusion turns uncertainty into a scored feature

The rubric explicitly rewards low-confidence handling. The fusion logic should therefore use two thresholds per signal, and anything between them should be treated as a deliberate REQUEST VERIFICATION outcome rather than an error. AWS recommends the same pattern: set liveness and face-match thresholds "after testing… on their specific content", and when a check is denied, retry or "send them to another method" ([AWS Face Liveness](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html)). The starting values below are anchored in published defaults wherever a default exists. Recalibrate all of them on the team's own captures by midday.

| Signal | Pass (contributes to ALLOW) | Uncertain (→ step-up) | Fail (→ DENY) | Anchor |
|---|---|---|---|---|
| Quality gate | all checks pass | any check fails → recapture hint (max 2) | — | engineering heuristics; IOD ≈ 63 px in Eyeblink8 ([CVWW 2016](https://vision.fe.uni-lj.si/cvww2016/proceedings/papers/05.pdf)) |
| PAD ensemble P_live (mean of 3 models, per frame) | ≥ 0.80 on ≥ 3 of 5 frames | 0.30–0.80, or < 3 frames live | ≤ 0.30 on majority of frames | InsightFace default 0.8 ([liveness.md](https://raw.githubusercontent.com/deepinsight/insightface/master/python-package/docs/liveness.md)); facenox 0.5→0.8 and 3–5 consecutive frames ([LIMITATIONS](https://raw.githubusercontent.com/facenox/face-antispoof-onnx/main/docs/LIMITATIONS.md)) |
| Device-in-frame detector | no phone/laptop/TV box contains face | low-confidence box near face | box (conf ≥ 0.4) contains face | COCO class 67 ([coco.yaml](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/datasets/coco.yaml)) |
| Flash response (chroma correlation, lag 1–3 frames) | r ≥ 0.7, stable lag | weak amplitude (bright room) or 0.3 ≤ r < 0.7 | r < 0.3 or wrong order/lag | Face Flashing timing + 3D checks ([NDSS 2018](https://www.ndss-symposium.org/wp-content/uploads/2018/02/ndss2018_03B-5_Tang_paper.pdf)) |
| Face match, Rekognition similarity | ≥ 99 (1:1) / ≥ 99 with no runner-up (1:N) | 80–99 | < 80 or no match | default 80 ([API](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_SearchUsersByImage.html)) |
| Face match, InsightFace cosine (fallback) | ≥ T_allow (start 0.50; set to the 99.8th percentile of impostor scores for 0.2% FAR); top1−top2 ≥ 0.10 | between T_deny and T_allow | < T_deny (start 0.30–0.35) | deepface Buffalo_L distance 0.55 ≈ similarity 0.45 ([threshold.py](https://raw.githubusercontent.com/serengil/deepface/master/deepface/config/threshold.py)) |
| Injection check | real camera device | unknown label | known virtual camera | judgement call; FIDO places injection outside PAD scope ([FIDO v4.1](https://fidoalliance.org/specs/biometric/requirements/Biometrics-Requirements-v4.1-fd-20250106.html)) |

Signals combine through an ordered rule set rather than a single opaque score, because judges and operators can follow a rule set. The rules treat two kinds of evidence differently. **Hard 2D-attack evidence returns DENY** with a reason code: a device box containing the face, a flash order/lag violation (the replay cannot follow the nonce), PAD failing on most frames, a known virtual camera, or a failed challenge (wrong action, or a response that arrives before the prompt). **Mask cues are softer.** They are: no expression deformation, a flat homography during a head turn, a non-skin flash spectral response, or an eye-hole border ring. Any one mask cue on its own routes to REQUEST VERIFICATION (step-up, OTP or a staff check), not DENY. Only two or more firing strongly together justify DENY. This rule is a design judgement, not a published standard. The reasoning is that each mask cue is also sensitive to lighting and pose, and a false DENY at a door costs more than one extra verification step. Next, a quality failure returns REQUEST VERIFICATION as a recapture. ALLOW requires PAD pass, flash pass (or flash uncertain only because of ambient light, provided PAD is strongly live at ≥ 0.9), match pass, no mask cue, and the same identity across first and last frame. Everything else is REQUEST VERIFICATION, and the step-up ladder runs as follows:

1. **Step 1, simple action:** a randomized two-step challenge, issued only after face lock. **One step must always be a deformation**: smile, open mouth, or puff cheeks. The other comes from blink, turn left or turn right. A blink-only check is defeated by a cheap paper mask with eye holes, of the kind included in the 3DMAD dataset, because the attacker's own eyes blink through it ([Idiap 3DMAD](https://www.idiap.ch/en/scientific-research/data/3dmad)). Paper and rigid masks cannot deform, so the `jawOpen` and `mouthSmile*` blendshapes stay near their neutral baseline, or the mesh loses tracking. Each step allows about 700 ms. A deformation passes when the blendshape rises more than about 0.4–0.5 above the neutral baseline taken in the first 200 ms, with a correlated shift of the cheek and nasolabial landmarks. A blink requires a close-then-open transition, using blendshapes > 0.5 then < 0.2. A head turn requires |yaw| > 15–20° in the commanded direction, and it doubles as a parallax test (see the next section). Any response that arrives before the prompt, or more than about 1 s after it, is rejected.
2. **Step 2, cloud fallback:** a Rekognition Face Liveness session where the sandbox permits it, accepting at a confidence of 80 or more. AWS's service card puts 50–60 against presentation attacks and 80–90 against injection, and notes that well-lit indoor settings support higher thresholds ([AI Service Card](https://docs.aws.amazon.com/ai/responsible-ai/rekognition-face-liveness/overview.html)). Its reference image then goes to `CompareFaces`.
3. **Step 3, OTP:** email through SES or Cognito, or an on-screen TOTP.

Two failed step-ups end in DENY. A pragmatic upgrade, if time allows, is a log-likelihood fusion (`logit(L) + logit(M)`) with two cutoffs fitted on the labelled test set and displayed alongside the rule set. Following AWS's operational advice, the kiosk should show only the decision and a reason, never raw scores, and should rate-limit to 5 failures per 3 minutes per device ([Recommendations](https://docs.aws.amazon.com/rekognition/latest/dg/recommendations-liveness.html)).

## Each attack scenario gets its own layered defense

HID's four scenarios do not share a single weakness, so the system should not rely on a single detector. The public research divides the defenses into texture/frequency CNNs, pseudo-depth supervision, rPPG, multispectral or depth sensors, and active flash. The TPAMI survey lists **flash** among the multimodal cues ([Yu et al., arXiv 2106.14948](https://arxiv.org/abs/2106.14948)). For an RGB webcam and a 2-second budget, the practical combination is a passive CNN, flash reflectance, and challenges that force parallax and deformation. rPPG and depth/IR are upgrades. The mapping below is a design inference, not a set of measured results. The notes found no per-attack numbers for MiniFASNet.

| Attack | Primary layer | Secondary layers | What makes it fail |
|---|---|---|---|
| Printed photo (A4, glossy) | MiniFASNet ensemble (texture, Fourier cues) | Flash: a print reflects but gives a flat, uniform shading response; head-turn **homography residual** (fit a planar homography to ~20 rigid landmarks across the turn; low residual means flat); paper-border/edge detection | Cannot follow a nonce colour with 3D shading; moves as a plane |
| Screen photo / video replay (phone, tablet, laptop) | Device-in-frame detector (COCO cell phone/laptop/TV) + FFT moiré | Flash: an emissive screen's chroma barely tracks the kiosk flash, and a replay cannot anticipate the nonce sequence; randomized challenge order | Bezel visible, moiré, wrong or late flash response |
| Eye-cut paper mask | Deformation challenge (smile, open mouth, puff cheeks) | Laplacian "ring" at the eye-hole border around the eye landmarks; homography flatness; PAD texture | Real eyes blink, but paper cannot smile; the eye-hole edge is visible |
| Rigid 3D mask (resin, plastic, 3D-printed) | Deformation challenge with correlated cheek/nasolabial shift | Flash **spectral** response (R/G/B reflectance ratios under red/green/blue flashes compared with a live-skin envelope calibrated on enrolled users); sharp uniform specular highlights; mouth interior misaligned with the mesh under "open mouth" | Correct 3D shape defeats parallax, but no expression and non-skin reflectance |
| Flexible silicone mask (stretch tier) | Route to REQUEST VERIFICATION or OTP on any weak cue | rPPG as a soft signal only; hardware upgrade to depth+IR or 850 nm NIR | RGB-only defenses are weak; be honest about it |

The mask rows deserve candour in the pitch. The high-fidelity HiFiMask benchmark has **54,600 videos and 225 realistic masks**. Its authors argue that "basic deep models and rPPG methods" which did well on older, small mask sets fall short in the real world ([Liu et al., arXiv 2104.06148](https://arxiv.org/abs/2104.06148)). Idiap's WMCA dataset records RGB, depth, IR and thermal specifically for PAD research. It even includes heated fake heads to defeat thermal-only checks ([Idiap WMCA](https://www.idiap.ch/en/scientific-research/data/wmca)). The stronger research models, such as CDCN++ (**0.2% ACER on OULU-NPU Protocol 1 and 6.5% HTER cross-dataset**), ship no weights and are research-only ([Yu et al., arXiv 2003.04092](https://arxiv.org/abs/2003.04092); [CDCN](https://github.com/ZitongYu/CDCN)). The credible roadmap slide therefore reads "RGB today; RealSense depth+IR for silicone masks next", not a claim that a webcam stops every mask. rPPG stays a soft cue: under 2 s it covers only about 1.5–3 heartbeats. It may push a decision toward REQUEST VERIFICATION, but it must never be the sole basis for ALLOW.

## The two-second budget survives only with interactive liveness off the main path

Rekognition Face Liveness is the obvious AWS answer, but it is the wrong primary path. The user has to fit their face to an oval and hold still while colours play, and AWS's own concurrency example assumes **"10 seconds × 5 TPS"** per session. Mumbai is capped at **5 TPS and 15 concurrent sessions** ([Rekognition quotas](https://docs.aws.amazon.com/general/latest/gr/rekognition.html)). Sessions are single-use and expire after 3 minutes ([CreateFaceLivenessSession](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_CreateFaceLivenessSession.html)). Its value lies elsewhere. It holds iBeta PAD Level 1 and Level 2 results of **100% TRR and 100% TAR at threshold 50**, though that service card dates from November 2023 ([AI Service Card](https://docs.aws.amazon.com/ai/responsible-ai/rekognition-face-liveness/overview.html)). That makes it a credible step-up and enrollment gate, and it lets the pitch claim an iBeta-tested layer behind the team's own fast path.

Define the 2-second SLA explicitly as **face lock to decision on screen**, and measure every segment with `performance.now()` and server spans. The figures below are estimates, apart from the published model timings, and they must be replaced with measured p50/p95 by mid-afternoon.

| Segment | Budget (ms) | Basis |
|---|---|---|
| Face lock + quality gate (browser, MediaPipe) | 200–300 | estimate; no published Landmarker latency ([MediaPipe](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)) |
| Capture window with 3–4 colour tint changes (~10–15 frames) | 800–1,000 | flash protocol design; keep ≤ 3 flashes/s for photosensitivity safety |
| Upload 3–5 JPEGs (~100–200 KB each) + chroma series | 100–300 | estimate on venue Wi-Fi to ap-south-1 |
| Server PAD: SCRFD + 3 MiniFASNet + FFT + flash analysis | 30–100 | SCRFD-10G 4.9 ms on unstated hardware ([model zoo](https://github.com/deepinsight/insightface/tree/master/model_zoo)); MiniFASNet ~2 ms on Pi 5 ([LiteRT](https://huggingface.co/litert-community/Silent-Face-Anti-Spoofing-LiteRT)); COCO detector dominates |
| Face match (parallel with PAD) | 200–500 | Rekognition "near real-time", no SLA ([FAQ](https://aws.amazon.com/rekognition/faqs/)); local ArcFace tens to ~150 ms (estimate) |
| Fusion + DynamoDB + response render | < 50 | DynamoDB single-digit ms (estimate) |
| **Total ALLOW path** | **≈ 1.3–1.9 s** | parallel A/B on the server is what makes this fit |

Three engineering choices protect the budget. First, keep compute warm. A single CPU EC2 instance running FastAPI has no cold start and the most predictable latency. Lambda is viable only with provisioned concurrency or SnapStart (Python 3.12+, but SnapStart cannot be combined with provisioned concurrency), because a cold start costs seconds ([Lambda SnapStart](https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html)). Second, send image bytes directly, avoiding an S3 round trip, and keep the Rekognition collection, compute and bucket in one region, since `SearchUsersByImage` requires a same-region bucket ([API](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_SearchUsersByImage.html)). Third, use **ap-south-1** for proximity to Bangalore, and keep us-east-1 as the fallback, which has higher quotas and is also a Liveness region ([quotas](https://docs.aws.amazon.com/general/latest/gr/rekognition.html)). The step-up path legitimately exceeds 2 s. Report it as a separate "verification time" metric so it does not pollute the headline number.

## Report ISO metrics with confidence bounds, not a single accuracy number

HID's target slide is a gift to a team that knows the standards, because an accuracy figure is not an ISO metric. ISO/IEC 30107-3 and the testing labs report **APCER per attack species (the worst species is the headline), BPCER for bona fide users, and IAPMR plus FMR/FNMR for the full system**. iBeta Level 1 uses six attack species with artefacts under $30. It aims for 150 attacks alternated with 50 genuine presentations, passes only at **0% penetration**, and caps BPCER at **15%** ([iBeta](https://www.ibeta.com/iso-30107-3-presentation-attack-detection-confirmation-letters/)). FIDO's biometric requirements supply the zero-error statistics. The 95% upper bound with no errors is **3/N** (1.61/N at 80%), FIDO's template is 15 subjects × 10 attacks per species, and FIDO v4.1 added deepfake video as a presentation-attack species ([FIDO v4.1](https://fidoalliance.org/specs/biometric/requirements/Biometrics-Requirements-v4.1-fd-20250106.html)).

The arithmetic shapes the protocol. Sixty attacks per species with zero errors bounds APCER below **5%**; 150 bounds it below **2%**. Supporting HID's **0.6% FRR** at 95% confidence needs about **500 error-free bona fide attempts**, and **0.2% FAR** needs about **1,500 impostor comparisons**. The impostor count is reachable offline by cross-matching every subject pair and padding with a public face set such as LFW. The FRR count is not reachable live in one day. The honest pitch line is therefore: "0 errors in N trials; 95% upper bound X%; here is the volume needed to confirm HID's target." Avoid the alternative of claiming "99.4%". iBeta itself stresses that results show conformance, not certification, so say "iBeta Level 1-style protocol", never "iBeta compliant".

The recommended one-day protocol uses about **8–12 subjects** with a deliberate spread of skin tones, glasses and beards, and **three lighting conditions** (office, backlit window, dim). It covers six species mapped onto HID's four scenarios: laser print, glossy print, phone-screen photo, laptop/tablet video replay, an eye-cut paper mask (the attack that specifically tests the deformation challenge), and an on-screen face-swap video. A 3D-printed or latex mask is reported separately as a stretch tier, because masks sit at FIDO Level B/C and iBeta Level 2. Interleave bona fide and attack attempts. Tune thresholds on a dev split of subjects and report on held-out subjects. If possible, hold one attack species out entirely to demonstrate generalization. The deliverables are a per-scenario confusion matrix, APCER per species with Wilson or Clopper-Pearson intervals, BPCER per lighting condition, FMR/FNMR with a DET curve, IAPMR (spoofs that pass PAD *and* match the target), step-up rate, and **p50/p95 decision time against the 2 s target**. For HID's "accuracy" framing, show the conversion explicitly: a system that rejects everything scores 75% accuracy on a 150:50 attack-to-genuine mix. That single sentence demonstrates why per-species reporting matters.

## Differentiators map directly onto the weighted rubric

The judging weights favour depth over feature count. The table below links each differentiator to the criterion it serves and to the evidence behind it.

|---|---|---|
| Risk-adaptive step-up: passive first, challenge or OTP only when uncertain | Problem-Solution Fit (25%), Usability (15%) | Keeps BPCER low for employees at a door while pushing APCER down; mirrors AWS's "risk-based decision" guidance ([AWS](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html)) |
| Kiosk/access framing: fixed camera, repeat cooperative users, throughput, "real-world conditions" | Problem-Solution Fit (25%) | HID's face products are kiosk and access oriented (U.ARE.U camera, Olea kiosks), and its October 2026 messaging stresses real-world conditions ([Biometric Update](https://www.biometricupdate.com/?s=HID+Global+face+liveness)) |
| Screen-flash reflection challenge with server-side timing verification | Innovation (20%) | Borrowed from Face Flashing and AWS's light challenge; defeats screen replay without extra hardware ([NDSS 2018](https://www.ndss-symposium.org/wp-content/uploads/2018/02/ndss2018_03B-5_Tang_paper.pdf)) |
| Separate injection-attack layer (virtual-camera detection, live OBS/DeepFaceLive demo) | Innovation (20%) | Injection is outside PAD testing and now certified separately under CEN/TS 18099; Innovatrics, HyperVerge and Idemia earned IAD certifications in late 2026 ([Biometric Update](https://www.biometricupdate.com/?s=CEN+TS+18099)) |

| Privacy by design: encrypted embeddings, KMS, TTL deletion, consent screen | Problem-Solution Fit | AWS makes the deployer responsible for notice and consent ([Recommendations](https://docs.aws.amazon.com/rekognition/latest/dg/recommendations-liveness.html)) |

For the presentation, use a live attack gauntlet rather than slides. Hold up a print, a phone photo and a laptop replay, and show the DENY reason code each time ("phone detected around face", "flash response mismatch", "screen moiré"). Then wear an eye-cut paper mask. It blinks, so a blink-only check would pass it. The system flags a mask cue, routes to REQUEST VERIFICATION, and denies the attempt when the "smile" step shows no deformation. Finally, show a genuine user in a backlit pose landing in REQUEST VERIFICATION and clearing a smile-plus-turn challenge. Close on the metrics table, with "HID target vs ours (95% upper bound)" and the p95 latency. Offering face plus an HID mobile credential as the final step-up factor ties the system to the sponsor's product line. Verify HID product names before putting them on slides; the notes could not reach hidglobal.com.

## Licences, masks and sandbox locks are the real failure modes

**Licensing is the risk teams most often miss.** InsightFace code is MIT, but its pretrained models, including `buffalo_l` and the new liveness add-on, are "for non-commercial research only" ([InsightFace](https://github.com/deepinsight/insightface/tree/master/python-package)). That is acceptable for a demo and fatal for a product without a commercial licence, which is one more reason Rekognition is the primary matcher. CelebA-Spoof is restricted to non-commercial research and may not be redistributed ([CelebA-Spoof](https://github.com/Davidzhangyuanhan/CelebA-Spoof)). Any model trained on it, facenox included, plausibly inherits that restriction despite its Apache-2.0 label, which is a grey area worth naming. CDCN is research-only and has no released weights ([CDCN](https://github.com/ZitongYu/CDCN)). FLIP has no code licence, and its paper is CC BY-NC-SA ([FLIP](https://github.com/koushiksrivats/FLIP)). pyVHR is GPL-3.0. The minivision MiniFASNet weights and their ports are clean Apache-2.0. Check the licence of whichever COCO detector you deploy, because the notes did not verify it: Ultralytics YOLO is commonly distributed under AGPL-3.0, and a permissive alternative would avoid the question.

**Masks and phone replays are the technical weak points.** facenox states plainly that it is "not trained on 3D silicone masks". It also notes that backlight causes errors and that faces need ±30° pose and at least 64×64 px ([LIMITATIONS](https://raw.githubusercontent.com/facenox/face-antispoof-onnx/main/docs/LIMITATIONS.md)). minivision warns that RGB-only robustness depends on camera and scenario ([minivision](https://github.com/minivision-ai/Silent-Face-Anti-Spoofing)). The most likely live failure is a judge holding a high-resolution phone replay. That is exactly where the device detector and the flash check must carry the decision, so rehearse it. A cut-out paper mask with real eyes behind it will pass a blink challenge, which is why every challenge includes a deformation step. Rigid 3D masks defeat parallax and partly defeat flash shading, so they depend on the deformation step and on the flash spectral response. Silicone masks deform, so they defeat RGB-only defenses outright and should be presented honestly as a stretch tier and a hardware roadmap item. The mask cues are also the signals most prone to false alarms in poor lighting. That is the reason for the rule that one mask cue on its own triggers step-up, never DENY. The flash check degrades in bright rooms and under camera auto-exposure. Try locking exposure through `applyConstraints` (support varies), and treat a weak signal as REQUEST VERIFICATION, never DENY. Rapid flashing is also a photosensitivity hazard, so use gentle tint transitions at no more than 3 changes per second and offer a non-flash path, as AWS recommends.

**The sandbox is an unknown.** The notes found no primary documentation on hackathon-account restrictions. Assume region locks, service control policies that deny GPUs or IAM role creation, no quota increases, and expiring credentials. Ap-south-1 defaults are 5 TPS for search and index and 25 TPS for `CompareFaces` ([quotas](https://docs.aws.amazon.com/general/latest/gr/rekognition.html)), which is fine for a demo but tight if judges hammer it concurrently. Use `CompareFaces` for 1:1 where possible and retry with jittered backoff. SMS OTP to Indian numbers requires TRAI DLT registration with PAN, TAN, GSTIN and CIN ([AWS SMS India](https://docs.aws.amazon.com/sms-voice/latest/userguide/registrations-sms-senderid-india.md)), which is impossible in a day, so use SES email (verified recipients in the SES sandbox) or an on-screen TOTP. Keep everything in Git with SAM/CDK or a single EC2 user-data script, and keep a fully local fallback on a laptop: FastAPI plus InsightFace plus MiniFASNet. Privacy hygiene stays the same either way. Use only consenting team faces, encrypt with SSE-KMS and the Liveness `KmsKeyId`, set S3 lifecycle and DynamoDB TTL, never log images, and run a teardown that deletes the collection.

## Conclusion

The judges' targets look like a demand for one very accurate model, but the problem rewards something else: a system that is accurate where it is confident and explicit where it is not. Four cheap, independent signals, namely a texture CNN ensemble, device-in-frame detection, a nonce-bound light reflection and an optional randomized challenge, cover each of HID's attack scenarios better than any single heavier model. FLIP's cross-domain numbers show that heavyweights still collapse on unseen masks and lighting. The REQUEST VERIFICATION band does double duty. It is the mechanism that holds FAR down without inflating FRR, and it is the rubric's "low-confidence handling" requirement, so build and demo it as a first-class path rather than an error state.

The second insight is that credibility is cheaper than accuracy. No team can validate 0.2% FAR in a day, and judges from a biometrics company know it. A team that reports worst-species APCER with rule-of-3 bounds and separates injection from presentation attacks is speaking the language HID's products are certified in. If it also names the licensing traps that would block commercialisation, it will likely outscore a team that claims 99.4% on a demo it tuned on itself. The architecture also points at a credible post-hackathon path: swap the non-commercial pieces for licensed matchers, keep the Apache-2.0 PAD and flash layer at the kiosk edge, and use Rekognition Face Liveness as the iBeta-tested step-up.

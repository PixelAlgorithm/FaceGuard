Can You Spot a Spoof?

FaceGuard is an HID entry kiosk that checks liveness, identity, the campus schedule and connectivity, then returns one clear decision.

ALLOW REQUEST VERIFICATION DENY

Team CipherTrust  ·  "Spot the spoof, check the schedule, never fail open."

FaceGuard1

Hi, we're team CipherTrust, and this is FaceGuard. The challenge was "Can you spot a spoof?": an HID entry kiosk has to tell a live person from a photo, a screen, a video or a mask, and decide within 2 seconds. We built that, plus both surprise challenges: campus schedule and offline mode. Every decision comes out as one of three colours: green ALLOW, amber REQUEST VERIFICATION, red DENY. Those colours stay the same through the whole deck.

THE PROBLEM

The same face can look real
and still not be the real person.

Printed photo

A4 print or an eye-cut paper mask with real eyes blinking through it

Screen replay

A photo shown on a phone or laptop held up to the camera

Video replay

A clip that blinks and smiles, so "is it moving?" is not enough

Mask (3D / printed)

Rigid or printed masks; silicone is the hardest case

Surprise 1: live is not authorised

A real, recognised student at the gate at 22:30 still should not get in. Biometrics have to be combined with the campus schedule.

Surprise 2: network down must not mean door open

When the central service is unreachable, the kiosk still decides, safely, and syncs the decisions later.

Why it matters: the kiosk is unattended, and one false accept opens a real door. HID's reference targets: liveness accuracy 99.4%, face-auth accuracy 99.2%, FAR 0.2%, FRR 0.6%, decision < 2 s.

FaceGuard · Problem2

Four attack types from the brief: printed photo, screen replay, video replay and masks. The eye-cut print matters because real eyes blink through the holes, so a blink check passes it. Then the two surprise challenges: a live, recognised person is not automatically authorised, and losing the network must never open the door. The kiosk is unattended, so a false accept is a security incident, not a UX bug.

FaceGuard · Architecture3

Three boxes. The kiosk browser finds the face and captures five frames while the screen flashes a random colour sequence. The edge service on the kiosk laptop does the real work: liveness and face matching run in parallel, then one policy engine applies biometrics, then the campus schedule, then the offline rules. AWS adds Rekognition, the authoritative schedule and the audit ledger when it is reachable. Because the edge always decides, losing the cloud is just a mode switch.

Fail-secure rules (enforced by tests)

Default is DENY. Any error returns DENY with SYSTEM_ERROR, never an open door.

Hard spoof evidence is final. No schedule, step-up or override can upgrade it.

Unsure never auto-allows. Every UNSURE signal routes to verification.

Each stage only tightens. Biometrics, then schedule, then mode.

Offline is stricter than online, never looser.

Every response carries decision, reason_codes, scores, latency_ms, mode.

FaceGuard · Decision policy4

Every signal has three zones: pass, fail, and an unsure band in between. Unsure never guesses: it asks for verification. Hard evidence like a phone in the frame is an immediate DENY that nothing can override. The step-up challenge always includes a mouth movement, because paper can't smile. And every decision carries reason codes, so the guard and an auditor can see exactly why. These rules are invariants checked by the policy test suite.

FaceGuard · Liveness5

We don't rely on one model. Two passive anti-spoof networks look at texture, a phone and screen detector looks for a device around the face, an FFT looks for the screen's moiré pattern, and a ring detector looks for mask edges. On top of that, a share of would-be ALLOWs get a random challenge, and it always includes a mouth movement. Two honest flags: the colour flash runs on every attempt but is advisory until we re-validate the webcam timing, and the iPhone depth app is built and integrated but stays off until it passes calibration.

INNOVATION · WHAT IS DIFFERENT HERE

Six ideas beyond "run an anti-spoof model"

Random colour-flash nonce

The server issues a fresh random 3-colour sequence per attempt; the screen flashes it in 700 ms and we check that the face reflects it. A replayed video can't know the colours in advance.

ADVISORY until frame timing is re-validated

Risk-adaptive step-up

Only unsure or risky attempts get a challenge. It always includes a mouth movement (smile / open mouth) plus a blink or turn, never blink-only: real eyes blink through an eye-cut print. Random on 15% of entries online, 30% offline.

ENFORCED

Early cloud probe

At face lock the kiosk sends one frame ahead, so Rekognition runs while the colour-flash capture is still happening instead of after it. A late answer is never waited for: that attempt is decided locally.

LIVE speed-up not measured yet

Signed schedule, last valid bundle

Schedules arrive as signed per-kiosk bundles evaluated on the kiosk. A bad or tampered bundle is rejected and never replaces the last valid one; with no valid bundle there is no ALLOW.

ENFORCED

Injection as its own layer

Virtual-camera label denylist (OBS, ManyCam...), frame-gap bounds of 15–400 ms and a single-use capture nonce. Reported separately from presentation attacks (CEN/TS 18099).

ENFORCED

Own iPhone TrueDepth app

DepthProbe, our SwiftUI app, streams TrueDepth depth to the edge so a flat print or screen can be caught by shape, not texture. Raises the bar for masks; it does not solve them.

FaceGuard · Innovation6

Six things set this apart. One: the colour flash is a challenge-response check with no extra hardware; the server picks the colours, so a pre-recorded video can't match them. We measure it on every attempt, but it stays advisory until we re-validate the webcam frame timing. Two: step-up is risk-adaptive and always asks for a mouth movement, because an eye-cut paper mask passes any blink check. Three: the early cloud probe starts Rekognition at face lock, overlapping it with the capture; if it's late, the kiosk decides locally rather than waiting. It's live, but we have not measured the gain yet, so no number. Four: the schedule is a signed bundle with a last-valid-bundle rule, so tampering can only deny. Five: injection attacks are their own layer. Six: we wrote our own iPhone depth app; it's built and connected but stays off until calibration.

A live, recognised person is not automatically authorised. Biometrics run first; only a person who passes, or is merely unsure, gets the schedule check. PRIVACY & SECURITY BY DESIGN

Store the minimum, sign everything

Privacy (India DPDP Act 2023)

  • Opt-in consent page at enrolment: no tick, no template
  • Templates, not images; no images stored offline, ever
  • Templates encrypted at rest (Fernet); log fields AES-256-GCM
  • Pseudonymous IDs, 2-dp scores, 24 h retention, purge on sync
  • Erasure: one call deletes the local template, TOTP secret and cloud user
  • Only consenting team faces; teardown script deletes them

Security

  • HMAC-SHA256 signed schedule bundles (Ed25519 in production)
  • HMAC-signed edge → cloud requests with a timestamp window
  • Single-use capture nonce: reuse is rejected
  • Injection layer: virtual-camera denylist + frame-timing bounds
  • Hash-chained decision log, verified on sync
  • Lockout after repeated attack attempts; raw scores only on the operator screen
FaceGuard · Privacy & security10

Privacy first: enrolment is opt-in, we keep templates rather than images, and offline nothing visual is ever written to disk. The offline log has pseudonymous IDs and rounded scores, is encrypted and is deleted within a day. On security: schedules are signed so a tampered file is rejected, every capture has a single-use nonce, and injection, meaning a virtual camera feeding a fake stream, is its own layer, separate from presentation attacks. The DPDP Act treats biometrics as personal data, and this is how we meet consent, minimisation and erasure.

What we would tell a security reviewer

Known limits today

  • Silicone masks deform like skin, a known limit of RGB. Depth raises the bar but doesn't solve it.
  • Colour flash is advisory until the webcam frame timing is re-validated
  • Depth is off until the DepthProbe calibration passes
  • Moiré and mask thresholds still need calibration on the eval dev split
  • Licences: InsightFace / CelebA-Spoof-trained weights are non-commercial

Not measured yet, so not claimed

  • No eval run yet: no APCER, BPCER, FAR, FRR or accuracy numbers today
  • Client face lock → decision latency: no stored measurement yet

SCALE & ROADMAP

From one kiosk to a campus fleet

How it scales

  • Edge per door, cloud per campus: each kiosk decides locally, so adding doors adds no work to the 2 s path
  • Per-kiosk bundles: each kiosk gets only its own zone, schedule and users' templates, signed for that kiosk
  • Idempotent sync keyed by attempt_id with a per-kiosk sequence, so many kiosks can reconnect at once
  • Ed25519 bundle signing: kiosks hold only the public key, so a stolen kiosk cannot forge a schedule
  • ap-south-1 (Mumbai) in production for DPDP data residency

Roadmap, in order

  • 1. Run the eval: iBeta Level 1-style protocol, ISO/IEC 30107-3 APCER / BPCER with bounds
  • 2. Calibrate moiré / mask bands on the eval dev split, freeze them, then score the test split
  • 3. Enforce the flash nonce after the kiosk frame timing is re-validated
  • 4. Depth go-live: enable TrueDepth after the 10 live vs 10 print calibration passes
  • 5. AWS Face Liveness as an optional cloud step-up, never on the 2 s path
  • 6. HID card / mobile ID fusion; CEN/TS 18099 injection testing; licensed matcher
Every roadmap item tightens or measures; none of them loosens the fail-secure rules.
FaceGuard · Scale & roadmap13

How this grows. Every door gets its own edge, every campus one cloud. Because the edge decides locally, adding doors doesn't slow anyone down. Each kiosk gets its own signed bundle with only its zone, its schedule and its users, and sync is idempotent, so a whole building coming back online at once is safe. The roadmap, in order: run the evaluation, calibrate on the dev split and freeze, enforce the flash, turn on depth after calibration, add AWS Face Liveness as a cloud step-up, then HID card and mobile ID fusion and formal injection testing.
